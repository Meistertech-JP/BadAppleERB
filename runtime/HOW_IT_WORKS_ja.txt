Bad Apple!! ERB — 文字映像の生成と再生の仕組み
================================================================

この文書では、元動画から数値モデルを生成する方法、そのモデルから
79桁×24行の文字映像を組み立てる方法、2種類の再生方式を説明する。
起動方法と操作は README_ja.md、英語版は HOW_IT_WORKS_en.txt を参照。

1. プログラムの構成
----------------------------------------------------------------

処理は、配布データを作るための生成処理と、ERBで実行する再生処理に
分かれる。生成処理では動画を読み込み、各行の明るい区間の位置と明度を
時間方向へ追跡し、整数値を再現する式へ変換する。再生処理では、指定された
フレーム番号についてその式を評価し、空白と色付きの「#」を組み立てる。

2種類の再生方式は ERB/PLAYER.ERB にまとまっている。いずれも同じ
BA_RENDER と BA_PRESENT、同じ数値データを使う。異なるのは、次に表示する
フレーム番号の選び方と、予定時刻に達するまでの待ち方である。

実行時に必要なのは、PyEmuera、ERB/ERH、CSV、同梱の数値データである。
元動画、FFmpeg、NumPy、生成用スクリプトは通常の再生では使用しない。
同梱PyPyはPyEmueraを動かすPython処理系として使用する。

基本仕様:

  論理画面             79列×24行
  明度                 0～255の256階調
  フレーム番号         0～6,572
  フレーム数           6,573
  時間軸               30 fps
  最終フレーム保持込み 219.100秒
  表示文字             半角の「#」と空白
  音声                 再生しない


2. 元動画から参照セルを作る
----------------------------------------------------------------

対象の元動画は sm8628149.mp4。映像は512×384画素、4:3、30 fpsで、
6,573フレームある。映像ストリームの時刻単位は1/15,360秒、フレーム間隔は
512単位である。最初の映像フレームのPTSは1,024だが、再生の時間軸では
最初のフレームを0秒にそろえる。

extract_reference.py はFFmpegで最初の映像ストリームをデコードし、次の
フィルターを適用する。

  scale=79:24:flags=area:in_range=tv:out_range=full,format=gray

元画像の全領域を79×24へ縮小する。切り抜きやレターボックスは行わない。
areaによる面積ベースの縮小を使い、入力のTVレンジを0～255のフルレンジへ
変換して、8ビットのグレースケール画像を得る。フレームは
-fps_mode passthrough で受け取り、抽出時に時刻合わせのための複製や
間引きを加えない。

明度を0と255の二値へ丸めないため、輪郭付近の中間色や光、フェードの
濃淡も0～255の値として残る。出力の主要配列は次の形を持つ。

  reference_frames.npz の gray
  dtype: uint8
  shape: [6573, 24, 79]
  要素数: 12,462,408

このgray配列が、一致を判断するための参照映像となる。生成処理のメタデータ
には、抽出条件、動画ストリーム情報、フレームのPTS、ハッシュを保存する。

同梱モデルに対応する識別値:

  元MP4のSHA-256
  9ca50d481a3e773a77f729ef7fcab3e1fe14cb3745eb3c97f6af72cccc3b7f7e

  gray配列をフレーム・行・列順に並べた生バイト列のSHA-256
  d9d69b416e4ed9d3b87465b0a003e038630ccf7a126054c045c9e76218052029

元動画、デコーダー、縮小処理の条件が変われば、参照セルの値も変わり得る。
既存モデルと同じ結果を確認する際は、参照データと抽出条件をそろえる。


3. 横方向の区間に分け、時間方向につなぐ
----------------------------------------------------------------

各フレームの各行を、同じ明度が連続する横方向の区間に分ける。黒、すなわち
明度0の区間は背景として扱い、明度が0より大きい区間を記録する。

1つの区間は、行番号、左端、右端、明度からなる。列の番号は0から始まり、
範囲は左端を含み右端を含まない [left, right) とする。例えば、1行の一部が

  明度: 0, 0, 128, 128, 128, 0, 255

なら、記録する区間は [2, 5)・明度128 と [6, 7)・明度255 の2つである。
黒い隙間は、再生時に区間の間を空白で埋めることで再現する。

次に、同じ行の前後フレームにある区間を対応づける。重なりが大きく、
左右の端点と明度が近い区間ほど、継続する同じ区間としてつなぎやすい。
対応づけでは左から右への順序を保ち、区間同士の順序が入れ替わらないように
する。前後でつながった区間の列を、トラックと呼ぶ。

対応する区間がなくなれば、そのトラックは消失する。新しく現れた区間には
新しいトラックを作る。各トラックには、出現フレーム、消失時刻、行番号、
出現時点で左隣になるトラックを記録する。区間が増減しても、生き残った
トラックは継続できる。

これは、画像から得た区間の時間方向の対応づけである。登場人物の骨格、
物体の名前、元の制作データにあるレイヤーなどを解析する処理は含まれない。
対応づけが決めるのは数値モデルのまとめ方であり、再現対象のセル値は
参照映像によって定まる。

同梱モデルのトラック数は259,787である。


4. 左端・右端・明度を独立した整数値の式にする
----------------------------------------------------------------

1つのトラックには、時間とともに変わる3つの値がある。

  LEFT  : 左端の列番号
  RIGHT : 右端の列番号
  GRAY  : 明度

3つの値は、それぞれ独立した区間に分割して式を当てはめる。明度が変化しても
左右の位置が同じ式で表せるなら、位置の区間まで分割する必要はない。逆に、
左右が動いても明度が一定なら、明度には長い定数区間を使える。

各区間は、開始フレームs、長さ、基準値b、傾きの分子pと分母qを持つ。
qは正の整数である。対象フレームをf、開始からの経過をdt=f-sとすると、
値は次の式で求める。

  value = floor(((2*b + 1)*q + 2*p*dt) / (2*q))

これは b + (p/q)*dt を、ちょうど半分の場合は上の整数へ丸める計算である。
例えば b=10、p=3、q=2 なら、dt=0,1,2,3 に対して10,12,13,15になる。
ERB側では式全体を整数演算で評価する。モデル生成時に分子が非負であることを
確認するので、ERBの整数除算でも上のfloorと同じ値を得られる。
p=0の区間は値が一定であり、再生側は基準値bをそのまま使う。

式の決め方

開始点の基準値bを固定すると、正の経過フレームtで観測値vを得る傾きには、
次の条件がある。

  (2*(v-b)-1)/(2*t) <= p/q < (2*(v-b)+1)/(2*t)

左側の境界を含み、右側の境界を含まない範囲である。生成処理は、各観測値から
得られる範囲の共通部分を求める。共通部分が残る間は同じ式の区間を延ばし、
空になる直前で区間を区切る。その範囲に入る有理数p/qを選べば、区間内の
すべての整数フレームで参照値を再現できる。

範囲の比較には整数の交差積を使い、浮動小数点の近さを判定基準にしない。
候補の傾きとして0や整数、小さい分母の有理数を選べる場合はそれを使う。
隣接する区間は重複せず連続し、次の区間は直前の区間の翌フレームから始まる。

一定速度に近い変化は長い区間にまとまり、複雑な変化は短い区間に分かれる。
1フレームの区間も使えるため、線形の式でまとめにくい箇所も表現できる。
映像の内容は元動画から得た数値データに含まれており、少数の手作りの式だけで
全編を記述する構成ではない。

同梱モデルの曲線区間数:

  LEFT     382,428
  RIGHT    383,004
  GRAY     756,496
  合計   1,521,928

生成処理はモデルを再評価し、参照セルとの不一致、区間の欠落や重複、
境界の不整合を調べる。結果は geometry_report.json に保存され、
全体の判定が失敗した場合はコンパイラーを非ゼロの終了コードで終了する。


5. 数値モデルを配布用データへ格納する
----------------------------------------------------------------

pack_geometry.py は、曲線区間から同じ係数組(b,p,q)をまとめ、共有辞書を作る。
同梱モデルには104,206個の係数組がある。辞書は ERB/GEOMETRY.ERH の
整数配列に格納する。各曲線区間は、その辞書の番号と継続時間を持つ。

曲線区間や出現・消失の情報は、txt00.txt～txt04.txt に格納する。
形式名は persistent-tracks-bmp15-v1 である。

15ビットの数値を表す1桁dについて、保存するUnicodeのコードポイントを
U+0100+dとする。dの範囲は0～32,767、コードポイントの範囲は
U+0100～U+80FFであり、UTF-16のサロゲート領域を通らない。
大きな識別番号は、基数32,768の下位桁・上位桁の2文字で表す。

  identifier = low + 32768*high

Unicode文字は数値を運ぶための容器であり、見えている文字の字形に意味はない。
これらのファイルに、表示済みの79桁のフレーム文字列を保存することはない。

各ファイルの内容:

  txt00.txt : LEFTの曲線。出現順のトラックごとに1行。
  txt01.txt : RIGHTの曲線。出現順のトラックごとに1行。
  txt02.txt : GRAYの曲線。出現順のトラックごとに1行。

    1区間を [継続フレーム数, 係数番号の下位桁, 上位桁] の3文字で表す。
    最初の区間はトラックの出現フレームから始まり、後続区間は連続する。

  txt03.txt : トラックの出現情報。出現順のトラックごとに1行。

    [出現フレーム, 行番号, 左隣の番号+1の下位桁, 上位桁] を保存する。
    左隣の番号+1が0なら、その行の先頭へ挿入する。

  txt04.txt : 各フレームで消失するトラックの番号。

    1番号は下位桁・上位桁の2文字。末尾の番兵フレームを含めて6,574行ある。
    そのフレームの出現処理より先に、消失処理を行う。

txt00.txt～txt03.txt は、それぞれ259,787レコードある。読み込み時には
期待されるレコード数を確認する。詳細な形式、件数、サイズ、SHA-256は
packed_format.json に収録している。

各ファイルはPyEmueraのLOADTEXTで扱う1ファイル16 MiBの範囲に収める。
最大の txt02.txt は5,464,257バイト。ERBの各数値配列も100万要素以内にし、
トラック×3チャンネルの状態配列は779,361要素となる。

改行に関する注意

レコードの区切りはLF、すなわちU+000Aだけである。数値として使用する
コードポイントにはU+2028やU+2029なども含まれ得る。そのため、Unicodeの
各種改行を自動的に区切りと見なす処理は使わない。ERBはUNICODE(10)を指定して
SPLITする。Pythonで扱う場合も splitlines() ではなく、明示的なLF区切りを
使う必要がある。再保存による文字コード変換やUnicode正規化も行わない。


6. 読み込み、状態の初期化、出現と消失
----------------------------------------------------------------

BA_LOAD は5つの数値ファイルをLOADTEXTで読み込み、LFで分割する。
一度読み込みが成功すると、そのプロセス内ではデータを保持する。
メニューから再び再生しても、同じファイルを毎回読み直す必要はない。

BA_INIT は、0～79個の空白と「#」の繰り返し文字列、および256種類の
<font color='#RRGGBB'> を用意する。R、G、Bには同じ明度を使う。
これらの小さな文字列を再利用し、各フレームの行の組み立てに使う。

BA_RESET は、24行の先頭トラック、出現情報の読み取り位置、処理済みの
イベントフレーム、現在の画像フレームを初期状態へ戻す。各トラックの曲線状態は
出現時に初期化される。読み込み済みデータの保持と再生位置のリセットを
分けることで、メニューから別の方式を選んでも先頭から再生できる。

生存中のトラックは、各行に1つずつある双方向連結リストで管理する。
トラックは前後のトラック番号を持ち、行の先頭からたどると左から右へ並ぶ。

BA_EVENTS は対象フレームで、まず消失するトラックをリストから外す。
対応する曲線状態も解放する。続いて、そのフレームで出現するトラックを、
出現情報に保存された左隣の位置へ挿入する。新しいトラックのLEFT・RIGHT・GRAY
それぞれの曲線区間を初期化する。

表示対象のフレームが大きく先へ進んだ場合も、その間の出現・消失イベントは
順番に処理する。これにより、目標フレームで存在する区間とその左右順が保たれる。
ただし、中間フレームの画像文字列を組み立てたり、表示したりする必要はない。


7. フレーム番号から24行の文字列を作る
----------------------------------------------------------------

BA_RENDER(f) は、0～6,572のフレーム番号fを受け取る。
以前の処理位置より手前のフレームを求められた場合は状態をリセットし、
先頭から必要なイベントを進める。前方へ進む場合は、残りのイベントだけを扱う。

各行について、先頭から生存中のトラックをたどる。トラックごとにLEFT・RIGHT・
GRAYの区間をそれぞれ進め、fを含む区間を選ぶ。その区間の係数と開始フレームから
4節の式を評価し、左端L、右端R、明度Vを得る。

行は次のように組み立てる。

  1. 前の区間の右端からLまでを、必要な個数の空白で埋める。
  2. 明度が変わった場合は前のfontを閉じ、Vに対応するfontを開く。
  3. R-L個の「#」を追加する。
  4. 次のトラックへ進む。
  5. 最後の区間から79列目までを空白で埋め、開いたfontを閉じる。

例えば明度128の区間は、<font color='#808080'> で囲まれた「#」になる。
fontタグは色の指定であり、表示上の列数に含まれない。完成した1行は、
色の情報を除いて常に79文字である。

生成した24本の行文字列は BA_ROW に保持する。次の表示対象のフレームでは
そのフレームの値から組み立て直す。数値モデル、短い繰り返し文字列、現在の
区間位置などは再利用するが、6,573枚の完成済み文字画像を保持する構成ではない。

フレームを省略したときの計算

時間同期で例えばフレーム32から40へ進んだ場合、33～40までの出現・消失を
処理し、フレーム40に存在するトラックだけを描画対象にする。曲線区間の
読み取り位置も40を含む区間まで進める。フレーム33～39の各行文字列は作らない。
イベントや曲線区間をたどる費用は必要だが、省略したすべての画像を描く費用は
発生しない。


8. 端末への表示
----------------------------------------------------------------

BA_PRESENT は、直前に表示した24行をCLEARLINEで消し、BA_ROWの各行を
1回ずつHTML_PRINTに渡す。最後にAWAIT 0を実行し、組み立てたフレームの
出力を反映する。HTML_PRINTのfont指定は、PyEmueraによって端末の文字色に
変換される。背景は黒に設定する。

画像は79桁×24行とし、80桁×25行の端末の右端・最下行に余裕を残す。
これにより、最右列への出力や最下行の改行による折り返し・スクロールを
避けやすくする。映像の再生中はメニュー、説明、計測結果の行を出さない。

起動スクリプトは標準エラーを logs/diagnostics.log に分けて保存する。
再生終了時の集計はOUTPUTLOGによって .pyemuera/logs に記録する。
メニューからの通常再生では、終了後にメニューを再描画する。


9. 時間同期の再生
----------------------------------------------------------------

メニューの1は BA_REALTIME を呼ぶ。数値データの読み込み、文字列の準備、
状態のリセットを済ませた後、最初のフレームを選ぶ時点を再生の開始時刻とする。
この時点からの計算と表示にかかる時間は、映像の時間軸に含まれる。

経過時間をelapsed_msとすると、現在の時刻に対応する番号は次のとおり。

  raw = floor(max(0, elapsed_ms) * 30 / 1000)
  target = min(6572, max(current_frame, raw))

最初はフレーム0を選ぶ。以後は実際の経過時間から対象を選び直す。
例えば経過1,340 msならrawは40である。前に表示したフレームが32なら、
次は40を計算して表示する。33～39を後から順番に再生することはない。

選ばれたフレームの計算・表示を終えた時点でまだ次のフレーム時刻より早ければ、
その時刻まで待つ。すでに遅れていれば待たずに時計を読み直す。これを繰り返す
ことで、描画処理の遅れを次々と累積させず、現在の時間軸へ追いつく。

1フレームの計算を途中で破棄する処理は行わない。選択したフレームを計算・表示
してから、次の時刻を選ぶ。このため、選択時刻から実際に表示されるまでには
そのフレームの計算・端末出力の遅延がある。時間同期は、その遅延がゼロになる
という意味ではなく、次の選択を実際の経過時間に基づいて行う方式である。

終端と最終フレーム

全編の終端時刻は ceil(6573*1000/30)=219,100 msである。
targetは6,572を上限とするため、大きく遅れた場合も最終フレームを計算して
表示する。最終フレームの表示が終端より早ければ、終端時刻までその画像を保持する。

進行中の処理が終端をまたぐと、その処理や最終フレームの計算・表示に必要な
時間だけ超過し得る。飛ばしたフレームを終端後にまとめて再生することはない。
したがって、超過は未表示の全フレームを処理する時間として積み上がることは
ないが、端末やOSを含む処理時間に対して固定のミリ秒上限を保証するものではない。

時計の性質

GETMILLISECOND() は使用するPyEmueraの壁時計に基づく時刻取得であり、
単調増加専用の時計ではない。式では経過時間を0以上にし、前回より小さい
フレーム番号を選ばないようにしている。システム時刻の補正や実行の一時停止は、
待ち時間やフレーム省略に影響する。

表示した番号、選択時刻、表示完了時刻は、映像の行を使わず内部で記録する。
終了時には表示数、省略数、最後のフレーム、経過時間、終端超過などを集計する。


10. 全フレームの再生
----------------------------------------------------------------

メニューの2は BA_PLAY を呼ぶ。フレーム0、1、2、...、6,572の順に、
毎回BA_RENDERとBA_PRESENTを実行する。処理が遅れても、次の番号は必ず1だけ
進むため、全6,573フレームが計算・表示される。

各フレームには、開始時刻から f*1000/30 ms の予定時刻を設ける。
計算が早く終わった場合は、前の画像を表示したまま予定時刻まで待ち、
その後に新しい画像を出す。予定時刻を過ぎていれば待たずに表示する。
最後のフレームの処理後も、全編の終端時刻より早ければそこまで待つ。

処理が30 fpsに間に合う場合は、元の時間軸に沿った再生になる。
間に合わない場合は、フレームを省略せずに処理を続けるので、全体の再生時間が
長くなる。連続するコマをすべて表示することが、この方式の優先事項である。

両方式の違いは、表示フレームの選択と待機に限られる。同じ番号fを計算した
結果の79×24セルは、どちらの方式でも同じ式とデータから得られる。


11. メニュー、静止AA、繰り返し再生
----------------------------------------------------------------

起動時の SYSTEM_TITLE は BA_MENU を呼ぶ。メニューは半角数字の文字列を
受け付け、1で時間同期、2で全フレーム、0で終了する。入力はEnterで確定する。
それ以外の入力では案内を表示し、同じメニューから再入力できる。

どちらの再生方式が終了してもメニューへ戻り、再選択できる。読み込み済みの
数値データは保持し、イベント位置や現在のフレーム、再生時計は各再生の開始時に
初期化する。前の方式で最後まで進んだ状態を、次の再生へ持ち越さない。

メニューには13行×73列の半角AAを組み込んでいる。大きなリボンの影絵、
中央のリンゴ、魔女帽子と箒の影絵をモチーフとする。AAはPLAYER.ERB内の
BA_MENU_ARTがPRINTLで表示する静止した装飾で、本編の数値モデルとは別に
用意した文字絵である。メニュー表示時にも外部画像を読み込む処理はない。

メニューの本文は23行に収め、入力欄と入力確定時の行に余裕を持たせる。
再生を選ぶと読み込み状態を表示してから本編へ移り、再生中はAAを表示しない。


12. 処理系と起動スクリプト
----------------------------------------------------------------

配布版の標準起動は、同梱PyPyでPyEmuera.pyzを実行する。
PyEmueraは3.0.0、PyPyは8.0.1のPython 3.12.15実装である。
PyPy上流では、このPython 3.12実装はbetaと位置づけられている。

起動スクリプトは自分のあるフォルダーへ移動し、logsを作ってから次の順序で
Python実行ファイルを選ぶ。

  1. 環境変数PYEMUERA_PYTHONに明示された実行ファイル
  2. 同梱のpypy/pypy3.exe、またはpypy/bin/pypy3
  3. システムのpython、またはpython3

PYEMUERA_PYTHONの値は実行ファイル名またはパスだけとし、追加の引数を
含めない。起動先には、診断ログと再生記録を保存するための書き込み権限が必要である。

WindowsのBadAppleERB.cmdは、PYTHONUTF8=1とPYTHONIOENCODING=utf-8を設定し、
同じフォルダーのconsole_utf8.pyを通してPyEmuera.pyzを起動する。
console_utf8.pyは、コンソールの入力コードページと出力コードページを別々に
保存してから両方を65001、すなわちUTF-8へ切り替え、Pythonの標準ストリームも
UTF-8にそろえる。エンジンの実行が終了すると、保存した入力・出力それぞれの
コードページを元へ戻す。コンソールの設定だけを起動時に整え、PyEmuera.pyz、
ERB、映像の数値データには変更を加えない。

Windowsで日本語が文字化けする場合は、同じ配布版のBadAppleERB.cmdと
console_utf8.pyをそろえて配置し、BadAppleERB.cmdから起動する。日本語が
四角で表示される場合は、端末フォントに日本語の字形が含まれることも確認する。

Windowsの BadAppleERB_CPython.cmd はPYEMUERA_PYTHON=pythonを設定し、
通常の起動スクリプトを呼ぶ。Linuxでは

  PYEMUERA_PYTHON=python3 sh ./run.sh

で同じ指定ができる。CPythonを使う場合の最低バージョンは3.10である。
いずれも同じERBを使い、Python処理系の選択によって映像データは変わらない。

Windows x64版のPyPyには、Windows UCRTとMicrosoft x64 Visual C++
ランタイムが必要である。Linux x86_64版はglibc 2.28以上を必要とする。
配布物に含まれるライセンス・告知はpypyとthird_partyに収録している。


13. 生成ソースと再生成の手順
----------------------------------------------------------------

生成ソース一式では、主に次のファイルを使う。

  extract_reference.py
    動画のデコード、79×24への変換、参照配列とメタデータの保存。

  compiler_geometry.py
    横方向の区間の追跡、3チャンネルの有理数式への変換、参照との比較。

  pack_geometry.py
    係数辞書の共有化、5つの数値ファイルとGEOMETRY.ERHの出力。

  runtime/console_utf8.py
    WindowsのコンソールをUTF-8に設定してエンジンを起動する補助ファイル。
    入出力の元のコードページをそれぞれ保持し、終了時に復元する。

  reference_frames.npz / reference_metadata.json
    抽出済みの参照配列と、その抽出条件・識別情報。

  persistent_gray/geometry_model.npz
    梱包前の数値モデル。

  persistent_gray/geometry_report.json
    モデルの件数や参照セルとの比較結果。

  requirements-build.txt
    生成・補助ツールのPython依存パッケージ。

再生成にはrequirements-build.txtに対応するPython環境と、同ファイルの
依存パッケージを用意する。Python 3.12を使用できる。同梱の
reference_frames.npzから数値モデルを再生成する場合、元のMP4やFFmpegは
必要ない。元動画から参照データ自体を抽出し直す場合に、MP4、FFmpeg、ffprobeを
使用する。元のMP4は実行用パッケージには含まれない。通常の再生では、
これらの生成用ツールをインストールする必要はない。

以下は生成ソースのルートで実行するPOSIXシェルの例。配布用runtimeを
別の出力先へコピーし、再生成したデータをそのコピーへ配置する。
rebuildは新しい出力用フォルダーとする。

  python3 -m pip install -r requirements-build.txt
  mkdir rebuild
  cp -R runtime rebuild/runtime
  python3 -B compiler_geometry.py reference_frames.npz --key gray --persistent --no-header --output rebuild/persistent_gray
  python3 -B pack_geometry.py rebuild/persistent_gray/geometry_model.npz rebuild/runtime

元動画から参照データを抽出し直す場合は、次を実行する。

  python3 -B extract_reference.py /path/to/sm8628149.mp4 rebuild/reference

その新しい参照を使うモデル生成と梱包のコマンドは次のとおり。

  python3 -B compiler_geometry.py rebuild/reference/reference_frames.npz --key gray --persistent --no-header --output rebuild/persistent_gray
  python3 -B pack_geometry.py rebuild/persistent_gray/geometry_model.npz rebuild/runtime

--key gray は256階調の配列を選び、--persistent はトラックを継続する方式を
選ぶ。--no-header は中間モデルの全曲線を巨大なERH配列として直接出力することを
抑止する。最終的な配布用GEOMETRY.ERHと数値ファイルはpack_geometry.pyが作る。

確認用の出力

BA_VERIFY は、通常の描画処理から得た全セルの明度をテキストとして出力する。
各フレームの先頭は「@FRAME 番号」、続く24行はそれぞれ79個の8ビット値を
2桁ずつの16進数にした158文字である。末尾には「@DONE 件数」を出力する。
端末のフォントやスクリーンショットを介さず、参照セルと比較できる。

  python3 -B runtime/PyEmuera.pyz runtime --entry BA_VERIFY --no-wait > trace.txt 2> diagnostics.log

BA_VERIFY_JUMPS は、大きな前方移動、同じフレームの繰り返し、後方移動などを
含む指定列を同じ形式で出力する。BA_REALTIME_AUDIT は実際の時間同期再生後に、
選択フレームと時刻の記録を出力する。これらはメニューとは別の開発用入口であり、
通常の視聴では指定する必要はない。


14. 何が一致し、端末で何が変わるか
----------------------------------------------------------------

数値モデルが再現する対象は、固定条件で縮小した79×24の参照セルである。
左右端と明度は整数式から求まり、同じフレーム番号なら再生方式に関係なく
同じ論理セルを得る。時間同期では、その中の時刻に対応するフレームを選んで
表示するため、画面に出るフレーム数は処理速度によって変わる。

端末の1文字は塗りつぶされた矩形画素ではなく、「#」の字形を持つ。
同じRGB値でも、フォントの線の太さ、文字内の空き、行間、端末の描画方法で
画面の見え方は変わる。元の512×384画素の細部を79×24セルの中にそのまま
保持することもできない。論理セルの一致と、端末上の物理的な画素の一致は
別の範囲を指す。

元画像の4:3に近い物理的な比率にするには、文字セルの幅をw、高さをhとして、

  (79*w)/(24*h) = 4/3
  w/h = 32/79
  h/w = 79/32 = 2.46875

となる。等幅フォントと端末の行間を調整し、文字セルの高さが幅の約2.47倍に
なると、全体の縦横比が4:3に近づく。

本編の表示領域、数値モデルの精度、フレームの選択方式、端末の字形は、それぞれ
独立した要素である。このプログラムは、79×24・256階調の定義済み映像を数値から
構築し、目的に応じた2種類の時間の進め方で表示する。
